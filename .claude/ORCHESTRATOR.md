# Opus routine runbook — triggered by Issue: Labeled (`agent:build`)

Use this runbook in the **Claude cloud scheduled task** whose model is Opus and trigger is GitHub `Issue: Labeled`, filter `agent:build`, repository `eyal-hl/red-light-rng`. The saved routine prompt should say: "Follow CLAUDE.md, AUTOMATIONS.md and .claude/ORCHESTRATOR.md for the issue in this GitHub event. Coordinate the subagents until reviewed PR and APK or needs-human."

1. **Guard.** Extract issue number from the actual GitHub event (never search for an arbitrary labeled issue). Verify event repo, an open non-PR issue, newly added `agent:build` label, and a **current independent Disagreer PASS with `ISSUE_SPEC_SHA256`** for latest GitHub title/body (`scripts/issue-spec-hash.mjs`). Verify independent authorization: either an authenticated owner `[AUTO-RUN AUTHORIZED]` top-level comment predating the initial `proposal` label event, or a separately authenticated explicit owner approval for this issue. Do not require that a planning-agent-applied build label itself be owner-authored; it is not authority. An automated label alone, stale PASS or untrusted comment is not approval. If any authorization/PASS cannot be verified, stop as `needs-human`. Do not infer PASS from silence. Do not start on this workflow-migration PR.
2. **Resume/dedupe.** Inspect PRs and branches for this exact issue, including `claude/` and legacy `agent/` branches. If one is already active, resume it only when safe; do not fork a duplicate. Serialized runs, cross-run leases and watchdog recovery are NOT provided by this prompt alone. If a separate active run cannot be ruled out, stop and ask rather than racing.
3. **Developer.** Choose `developer` (Haiku) for small changes; choose `developer-sonnet` (Sonnet) for complex DB/GPS/architecture or failed Haiku. Have worker code on isolated working branch. The lead creates/updates ONE PR based on `main` with issue link. Claude cloud branches may be `claude/*`; do not assume `agent/*`.
4. **Independent checks.** Invoke `reviewer` (Sonnet) and `qa` (Haiku) in parallel in separate contexts for the SAME SHA. Collect both results and CI. Keep QA's human-device limitations separate. Never count stale SHA results as passing.
5. **Repair.** Combine actionable review+QA findings into ONE `fixer` (Haiku) pass on same branch. After one failed/no-progress Haiku attempt use `fixer-sonnet`. Review+QA rerun on each changed SHA. Stop after 3 repair rounds total or sooner on repeat/no-progress/unresolved safety risks; report `needs-human` with evidence and links.
6. **APK.** Existing `.github/workflows/pr-android-apk.yml` builds signed Android preview APK for same-repository PRs with `EXPO_TOKEN` and EAS-managed signing credentials. Check the workflow run and APK artifact for **latest PR SHA**. Never regenerate credentials, claim signing-key parity without comparing against the installed app, or equate `expo export` with an APK. On build/auth/signing failure report blocker.
7. **Completion.** Comment on the PR/issue with exact SHA, reviewer+QA status, tests, APK workflow/artifact, remaining Android physical steps and iOS unvalidated. Mark ready for physical QA or human merge as appropriate. Never merge without explicit owner permission. If no PR or APK is possible, clearly state what remains and why; do not claim background persistence beyond the current routine run.

Use the account's Claude subscription, not an Anthropic API key or API billing. Keep model costs within subscription limits; extra usage and external services must not be silently enabled.
